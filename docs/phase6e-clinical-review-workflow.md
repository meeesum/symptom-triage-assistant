# Phase 6e deep-dive: clinical review workflow

Fifth and final epic of the scale-up roadmap's Phase 02 (Clinical Depth),
depending on `docs/phase6b-knowledge-base-expansion.md` — the reviewer
queue that epic's `reviewed` field always pointed toward but never had a
mechanism behind it.

## What's built

- `app/models/kb_review.py` — `KbArticleSubmission`: one row per
  submission, not per article. An article's edit history is every row
  sharing its `article_id`, ordered by `version` — that's the version
  history the roadmap epic asked for. Nothing is ever overwritten or
  deleted: a rejected submission stays in the table permanently, and an
  approved submission never retroactively changes what an earlier
  approved version said.
- `app/services/kb_review.py` — `submit_article()`, `list_submissions()`,
  `get_article_history()`, `approve_submission()`, `reject_submission()`.
  `approve_submission()` is the one that actually matters:
  1. Writes the article to `data/knowledge_base/articles/{id}.json` via
     `app/rag/knowledge_base.py`'s new shared `write_article_file()` (now
     also used by `scripts/kb_ingest.py`'s CLI, so the file format is
     owned in one place, not duplicated).
  2. Stamps `reviewed: true` — the first time anything in this codebase
     has ever set that field to `true` on a real article, closing the
     gap `docs/phase6b-knowledge-base-expansion.md` explicitly left open.
  3. Calls `get_default_retriever.cache_clear()` — without this, an
     approval would be invisible to every already-running server process
     until its next restart, defeating the point of a *live* review
     workflow. See "verified live" below.
- `app/api/kb_review.py` — `POST /kb-review/submissions`,
  `GET /kb-review/submissions?status=`, `GET /kb-review/articles/{id}/history`,
  `POST /kb-review/submissions/{id}/approve`,
  `POST /kb-review/submissions/{id}/reject`. All five endpoints gated to
  `provider`/`admin` roles via the existing `require_role()` — a
  "credentialed reviewer," reusing the role that already means clinical
  credential in this codebase (see `app/models/user.py`) rather than
  inventing a new one.
- `migrations/versions/ae8b435b2f07_*.py` — real Alembic migration for
  the new table, autogenerated and reviewed, following the same
  Postgres/SQLite-portable pattern as every other migration in this repo.

## Self-review is blocked, deliberately

`approve_submission()` and `reject_submission()` both reject with
`SelfReviewNotAllowed` (surfaced as a 403) when the reviewer is the same
user who submitted the draft. A "review workflow" where the author can
approve their own work isn't actually a review — it's the same
single-person-authorship the placeholder KB already had, with an extra
API call in between. This is a real, enforced constraint, not just a UI
convention: verified in both `tests/test_kb_review_service.py` and
`tests/test_kb_review_api.py`, and live (see below) with two genuinely
different provider accounts.

## Verified live, not just tests: approval takes effect without a restart

Ran the real dev server and drove the actual API with curl, using two
separate real provider accounts (not the same account wearing two hats):

1. Registered `author1@example.com` and `reviewer1@example.com`,
   bootstrapped an admin directly in the DB (same pattern
   `scripts/create_admin.py` uses), promoted both to `provider` via the
   real `PATCH /admin/users/{id}/role` endpoint.
2. As the author: submitted a draft article with a unique marker
   sentence (`live_test_topic_zzz`, containing the word "zzzqux" — chosen
   specifically so it couldn't already exist anywhere in the corpus).
3. Confirmed the article file did NOT exist on disk yet.
4. As the reviewer (a different logged-in account): approved the
   submission with a review note.
5. Confirmed the file now exists on disk with `"reviewed": true`.
6. **Without restarting the server process**, queried
   `POST /triage/intake` with text containing "zzzqux" — it correctly
   retrieved and cited the newly approved article, proving
   `get_default_retriever.cache_clear()` actually works end-to-end, not
   just in a unit test with a mocked cache.
7. Cleaned up: deleted the test article file and the test database
   before finishing, so nothing from this verification run was left in
   the repo.

## What's still open

- **No frontend UI.** This epic is backend-only — a reviewer today has to
  call the API directly (or via `/docs`, since FastAPI generates
  interactive Swagger UI for every endpoint here). A review-queue page in
  the frontend (list pending submissions, approve/reject with a note) is
  natural follow-up work, not included in this pass — the roadmap's own
  loc estimate for this epic (~900 loc) is backend-workflow-sized, not
  full-stack-sized.
- **No `article_id` validation against `rules.yaml`.** A reviewer can
  approve a submission for an `article_id`/`tags` combination that
  doesn't correspond to anything in `rules.yaml` at all — nothing here
  reuses `scripts/kb_ingest.py check-coverage`'s logic to warn a reviewer
  "this doesn't close any actual citation gap." Worth wiring in, not done
  here.
- **No diff view for edits.** Submitting a second version of an existing
  `article_id` is supported (version increments, history is queryable),
  but nothing shows a reviewer WHAT changed between the current live
  article and the new draft — they'd need to compare the JSON files
  themselves.
- Still explicitly placeholder content even once approved — this
  workflow verifies a submission went through a second pair of eyes, not
  that the underlying medical claim is independently sourced.
  `source_type` stays `"placeholder"` through approval; only `reviewed`
  flips. See `docs/phase6b-knowledge-base-expansion.md`'s same caveat.
